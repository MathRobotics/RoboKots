# Rust独立化とモデル構築の改善方針

計画策定時の基準コミット：`1e31b3e`。下記の対応状況を除く計画・基準時点の記述は、未実装の機能保証ではない。

## 現在の対応状況（2026-09-23）

- Rust入力を明示したJSON・辞書・URDFでは、Pythonの完全なモデル生成を省略する。JSON解析・モデル検証はRust、URDF解析は既存Python readerを使う。
- 軽量なModelInfo、型付き出力指定、world状態値取得、状態更新、RNEA/ABA、selected微分をRust公開APIから利用できる。Pythonなしの外部crateテストで確認している。
- PythonモデルはNumPy/JAXなどで必要になった時点で展開する。NumPyモードの状態・エネルギー・逆/順動力学・キャッシュはRust拡張に依存しない。
- 運動学の密ヤコビ行列と直接積は祖先経路の係数を利用する。通常トルクのJv/JᵀvはRNEAの局所微分を再利用し、密行列を生成しない。
- 未対応として残るのはURDF readerのRust移行、モデル編集・交換時の同期規約、CMTM系の直動関節対応拡大、独立配布・非公開化。高次トルク・動力学混在要求のさらなる高速化も別途検討する。

利用方法は[開発ガイド](README.md)、今回の直接積の速度比較は
[Jv/Jᵀv比較](benchmarks/results/rust_products_comparison.md)を参照。
以下の「棚卸し後の実装」から「追加変更」までは実装の経過、その後の各項目は当初の計画として残す。

## 目的と優先順位

優先するのは、Rustでモデルの読み込み・構築・計算を完結できることと、Rustだけを使う場合にPythonでモデル全体を展開しないこと。
JSONへの受け渡し変更そのものを目的にしない。入力形式にかかわらず、Pythonでモデルを構築してからRustで再構築する重複を減らす。
将来の非公開リポジトリへの移行・バイナリ配布に備えるが、当面は同じリポジトリ内で境界を整える。

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | Pythonモデルへの依存と必要情報の棚卸し | Rust計算経路が必要とする情報・操作・変更通知が一覧化される |
| 2 | Rustの計算入口と状態操作の整備 | 別のRust利用側から、モデル生成・状態計算・微分をPythonなしで実行できる |
| 3 | Rustによるモデル読み込み | 選んだ入力形式で、Pythonオブジェクトを作らず共通の型付きモデルへ変換できる |
| 4 | Python側のモデル展開を必要時に限定 | Rustのみの通常経路でRobotStruct生成・モデル辞書化が呼ばれない |
| 5 | 配布と非公開化の準備 | ソース配置に依存せずwheelでインストール・計算・検証できる |

各段階を独立した変更単位にし、検証後に進める。大規模な一括書き換えや計算実装のコピーは行わない。

## 棚卸し後の実装

軽量なModelInfoと、outward/batch状態操作・selected直接積・ABAのnative操作を追加した。
PythonのRust状態adapterとRust微分選択は、名前・番号・自由度を軽量情報から取得する。
Rustの外部利用側からのintegration testを用意している。詳細は[開発ガイド](README.md)を参照。
次は入力検証とモデル交換の規約を固め、Rustの読み込み経路とKotsの生成を接続する。
以下の現在地は基準コミット時点で、完全なPythonモデルを作らない初期化はまだ未実装。

### 入力入口の追加変更

`backend="rust"`付きのJSON/辞書/URDF入力は、RobotStruct生成・再辞書化を省略する。
JSON解析とcanonical入力の検証はnativeへ移し、URDFは既存Python readerの出力を直接渡す。
完全なPythonモデルはNumPy/JAX等の利用時に一度だけ展開する。Rust-only crateからのJSON読込も追加した。
URDF reader自体のRust移行、モデル編集・交換時の同期、残るworld状態値変換は未対応。
詳細と速度比較は[開発ガイド](README.md#native-first-model-input)を参照。

### world状態値・Rust公開APIの追加変更

world空間運動の値取得をnativeへ移し、公開Python経路もそのgetterを使うようにした。
Rustの出力指定をStateOutput/StateOwner/StateQuantity/ReferenceFrameに整理し、RNEA/ABAの単体・バッチ入口を公開した。
詳細と検証は[開発ガイド](README.md#native-world-values-and-typed-calculation-api)を参照。
過去の節に残るworld状態値変換の未対応記述は、この変更前の記録である。

## 現在地

- エラー型、型付きモデル、モデル構築、状態容器とその生成はRustに分離済み。
- `py_api.rs` のPythonクラスがnativeの値を直接保持する。PyO3とNumPyは任意依存。
- Pythonなしのビルドとcrate内テストは可能。ただし、外部Rust利用側に必要な計算メソッドの多くはまだcrate-private。
- `Kots` は引き続きPythonの `RobotStruct` を保持し、Rustモデル生成時に辞書へ変換する。
- 状態指定・出力取り出し・キャッシュ操作の一部はPythonまたはPythonバインディングに残る。
- 直動関節は対応するRNEA等の経路と、固定・回転関節に限定される経路がある。モデル型で表現できることと、全計算で対応することを混同しない。

性能の根拠は[遅延の切り分け](benchmarks/results/native_boundary_diagnosis.md)を参照する。
小さなモデルでの生成時間は約0.5µs増加したが、繰り返し計算での2〜4%の遅延は交互測定では再現しなかった。
この結果だけを理由に安全性検証を削除したり、計算カーネルを複雑化したりしない。

## 1. 必要情報の棚卸し

静的な棚卸しを実施し、[Python依存の棚卸し](python_dependency_audit.md)に記録した。
次は軽量なモデル情報の契約とnative状態操作の具体化へ進む。全経路の動的検証は未実施。
以下は棚卸しの対象とする。

| 対象 | 確認する内容 |
| --- | --- |
| `kots.py`、`api/rust_backend.py` | モデル生成、自由度、motion配置、モデル更新時のキャッシュ無効化 |
| `core/state/spec.py`、`api/rust_derivatives.py` | 名前から番号への解決、所有者、出力幅、展開順、対応可否 |
| `outward/rust/model.py`、`outward/rust/data.py` | 辞書化、Pythonモデルを参照する状態生成・出力処理 |
| `robot_io.py`、`urdf_io.py`、`core/robot.py` | 読込・既定値・検証・座標系・関節順序の規約 |
| NumPy/JAX計算、可視化、モデル出力 | 完全なPythonモデルが必要になる条件と保持すべき情報 |

成果物は、最小限のモデル情報の一覧、Rust側に移す操作の一覧、既存APIへの影響と対応範囲とする。
名前・番号・自由度・motion配置・対応機能は候補だが、棚卸し前に新しい汎用プロトコルやクラス階層を確定しない。
元ファイルだけではPythonで編集した後の状態を再現できないため、モデル編集と更新通知も対象にする。

## 2. Rustの計算入口を整える

- 外部利用側が必要とする少数のメソッドを公開する。内部配列・全カーネルを一括で公開しない。
- 状態更新、selected出力の要求検証、JVP/VJPの実行とキャッシュ管理をnative側へ順に移す。
- PyO3側は入力配列の借用・形状確認・出力変換・例外変換へ責務を絞る。
- `StateCache` の意味上の状態と、Rustの計算用ワークスペースを混在させない。
- Rust単独の利用例とintegration testを作る。crate内テストだけで外部利用可能とは判断しない。

完了条件は、対応範囲のモデルについて、外部利用側から型付きモデル生成→状態計算→dense/JVP/VJPを実行し、独立した参照と比較できること。
未対応関節・次数・座標系は明示的にエラーにし、JVP/VJPを密行列経由へ置き換えない。

## 3. 入力形式とモデル構築を分ける

各入力の読み込み処理は共通の `RobotModel` に変換し、検証・コンパイル・計算を共有する。
既存JSON・URDFのどちらから移すかは、利用頻度と既存仕様の調査で決める。最初から両方を完全実装しない。

特に確認するもの：

- 名前・外部IDと内部番号の対応、親子順序、固定関節、motionの並び。
- 原点姿勢、軸、慣性の参照位置・座標系、既定値、単位。
- URDF等の未対応要素、モデルJSONのschema version、無視してよい情報と拒否すべき情報。
- 可視化・書き出しで使う名前、形状、付随情報。計算用情報だけ残して復元不能にしない。

完了条件は、対応形式・対応要素を文書化し、既存Python読込とRust読込から得たモデルの運動学・動力学が一致すること。
ファイルを読む経路と、すでにメモリ上にある定義を渡す経路を区別して計測する。

## 4. Pythonでは必要な情報だけ持つ

- Rust経路では、Rustモデルへの参照と必要なモデル情報だけを保持する。
- NumPy/JAX計算、編集、可視化で必要になった時点でPython側の構造を生成する案を優先する。
- PythonとRustのどちらを更新の正本とするかを操作単位で定め、二つのモデルを暗黙に同期させない。
- 当初はコンパイル済みRustモデルを不変とし、編集時に再構築して関連キャッシュを無効化する方式を候補とする。
- Pythonモデルが必要な未対応機能へ移る際の明示的な変換・エラー方針を決める。高速経路で黙って全モデルを展開しない。

完了条件は、Rustだけを使う読込→状態→微分のテストで、Pythonモデル生成・辞書化を呼ぶと失敗する検査が通ること。
併せてバックエンド切替、モデル編集後の値・名前・番号・キャッシュの整合性を検証する。

## 5. 配布・非公開化は境界が安定してから

- Rustソースとビルド・内部テストを将来分離できる状態にする。別実装へのコピーは行わない。
- 対象OS・CPU・Python版を決め、wheelのビルドとクリーン環境での導入試験を用意する。
- Python APIと拡張の互換性を確認できる版管理・エラー表示を用意する。
- 実際の非公開化では、公開履歴・ライセンス・NumPy参照実装の扱いを確認し、公開対象を別途決定する。

Rustの高速実装だけを守るのか、計算方式の実装全体を守るのかで、NumPy側の公開方針も変わる。
この計画の作成だけでソース削除、公開範囲変更、外部への配布は行わない。

## 共通の性能・正確性評価

計測を次に分ける：ファイル読込・解析、型付きモデル構築、コンパイル、初回状態計算、計算済み状態、キャッシュヒット・ミス、モデル更新。
Pythonオブジェクトの展開を減らす段階では、時間だけでなくピークメモリと保持メモリも測る。
小規模・多自由度・分岐・固定関節を含むモデルを用い、単体・バッチ・dense・JVP・VJPを分ける。

比較では同一入力・dtype・重力・次数・出力順を使い、ビルドやテストと同時に測定しない。
短い処理はAB/BA交互測定と未変更の対照処理を用い、初回費用・warmup・生サンプル・環境・バイナリの識別情報を保存する。
別プロセスでの起動性能と同一プロセスでの計算性能を混同しない。根拠なく一律の「数%以内なら合格」は設定しない。

数学的な変更や読込規約の変更は、数値差分・NumPy等の別経路と比較し、最大絶対差・相対Frobenius誤差を記録する。
モデルの正しさ、local/world、高次微分、重力、出力順序を優先し、性能改善のために規約や検証を省かない。

## 当面後回しにするもの

- JSON化するだけの受け渡し変更。
- 約0.5µsのモデル生成差だけを狙う複雑な最適化。
- 独立化と同時に行う対応関節・柔軟モデルの大幅拡張。
- 実測に基づかないGIL解放・並列化・データ構造の全面変更。
- 境界が未確定の段階でのリポジトリ分割。
